# Metadata & index formats

The launcher config is **two layers**:

1. **`GAME.TXT`** — human-edited metadata next to each game (source of truth).
2. **`GAMES.LST`** — machine index generated by `dgb.py scan` (what `BROWSER.COM` reads).
3. **`DGB.CFG`** — optional runtime path config (`GAMES_ROOT`) generated by setup/scan tooling.

Do not hand-maintain `GAMES.LST` unless you know you need to; re-run the scanner after any catalog change.

---

## Per-game `GAME.TXT` (source of truth)

Place next to the game files, e.g. `GAMES\JILLOFTH\GAME.TXT`:

```ini
title=Jill of the Jungle
year=1992
genre=Platform
publisher=Epic MegaGames
exe=JILL.EXE
setup=
note=Epic MegaGames shareware platformer
```

| Field | Required | Notes |
|-------|----------|--------|
| `title` | yes* | Display name (*defaulted from folder if missing) |
| `year` | no | `1980`–`2099` |
| `genre` | no | Single primary genre (Action, Platform, …) |
| `publisher` | no | |
| `exe` | yes* | Launch file name in the game’s working directory |
| `setup` | no | Optional setup/config program (not used by v1 browser UI) |
| `note` | no | Shown in detail pane (one line; ~40 chars stored in index) |

Lines starting with `#` are comments. Keys are case-insensitive.

### Autogeneration

```bash
# After adding or changing games:
python dgb.py scan --games-root <games> --launcher-dir <launcher>

# Prefer catalog titles/years when GAME.TXT is incomplete:
python dgb.py scan --games-root <games> --launcher-dir <launcher> --apply-catalog

# Sort options: genre (default), year, title
python dgb.py scan --games-root <games> --launcher-dir <launcher> --sort year
python dgb.py scan --games-root <games> --launcher-dir <launcher> --no-headers
```

If `exe=` is missing, the scanner picks a launch file from `.EXE` / `.COM` / `.BAT`, preferring names like `start.bat`, `jill.exe`, `keen1.exe`, and skipping `setup.exe`, `cwsdpmi.exe`, `catalog.exe`, etc.

## Generated `GAMES.LST` (browser index)

Built by `dgb.py scan`. Written with **CRLF** and ASCII. The ASM browser reads this file from the launcher directory (with fallback to `C:\GAMES.LST`).

When the launcher is installed in a dedicated directory such as `C:\DGB\`, the browser reads `C:\DGB\GAMES.LST` and resolves game directories using `DGB.CFG` `GAMES_ROOT` (defaulting to `\GAMES`).

```text
# comment
H|Action
G|BOUNCYBA|BOUNCYB.COM|Bouncy Ball|1983|Action|Public Domain|Short note
G|SNAKEMIN|SNAKEMI.COM|Snake Mini|1990|Action|Public Domain|
H|Platform
G|JILLOFTH|JILL.EXE|Jill of the Jungle|1992|Platform|Epic MegaGames|
```

| Kind | Fields |
|------|--------|
| `H\|title` | Section header (not launchable) |
| `G\|dir\|exe\|title\|year\|genre\|publisher\|note` | Game |

- `dir` is relative to the launcher directory’s `GAMES\` folder (may include subdirs, e.g. `COMMANDE\KEEN`)
- At launch: `CHDIR` to `<games_root>\<dir>`, then `EXEC` `<exe>`
- ASCII only

### Limits

| Limit | Value | Enforced by |
|-------|-------|-------------|
| Entries (games + headers + spacers) | **320** | `MAX_ENT` in `src/browser.asm` |
| Line length | **160** characters | `MAXLINE` in `src/browser.asm` |
| Total file size | 65535 bytes | 16-bit file offsets in the entry table |
| Stored title | 32 characters | `TLEN` |

`dgb/limits.py` reads `MAX_ENT` and `MAXLINE` straight out of `src/browser.asm`,
and the scanners refuse to write an index that exceeds them, so the launcher can
never silently truncate a catalog. Each category header also consumes a blank
spacer slot, so `--no-headers` buys back roughly two slots per genre.

While a game runs, the browser hands its entry table (11.5KB) back to DOS and
rebuilds it when the game exits, so a child sees roughly 624KB free rather than
612KB. Games that report "Out of memory! Try Unloading TSRs!" are sensitive to
exactly this.

The browser keeps only type, title and a file offset per entry in memory; year,
genre, publisher, note, dir and exe are re-read from `GAMES.LST` on demand. That
is why the entry ceiling could rise from 64 to 320 while `BROWSER.COM` got
*smaller*: 24.6KB before, 8.7KB now.

The entry table itself is never written into the `.COM`. A DOS `.COM` owns its
whole segment, so the table lives past the end of the image — it costs address
space and nothing on disk, which is why `MAX_ENT` can be generous.

## Runtime `DGB.CFG`

Written by `dgb.py scan`. `GAMES_ROOT` comes from `--games-root-dos`, or is
derived from an explicit `--image-root`. It is never inferred from host directory
layout, so a wrong value cannot be guessed into place; if neither option is given
the scanner says so and skips the file.

```ini
; DOS Game Browser runtime config
GAMES_ROOT=\GAMES
```

- `GAMES_ROOT` is the DOS root used to resolve `dir` values from `GAMES.LST`.
- If missing, launcher defaults preserve legacy behavior (`GAMES\` and `\GAMES\` fallback).

## Sample catalog (`tools/sample-catalog.json`)

Used by:

- `dgb.py samples` — download free/shareware packs into `your games directory`
- `--apply-catalog` — fill missing metadata fields from the sample catalog

Extend the JSON when you want a reproducible demo set without committing binaries.

### AI-assisted metadata cleanup

After scanning a mounted DOS image, you can use an AI agent to help fill in missing `GAME.TXT` fields. Keep the output conservative and review it before rescanning.

Prompt template:

```text
You are helping prepare a DOS game launcher catalog.

I have a folder tree under your games directory with DOS game binaries and per-game GAME.TXT files generated by a scanner.

Task:
- Inspect the discovered binaries and existing GAME.TXT files.
- Infer the most likely title, year, genre, publisher, executable, setup program, and one-line note.
- Keep entries accurate and conservative; do not invent facts when the binary name is unclear.
- Prefer the real launch executable over setup or catalog tools.
- Preserve DOS 8.3-friendly filenames and backslashes in paths.
- Output only the updated GAME.TXT contents, one file at a time.

If information cannot be determined with confidence, leave the field blank and say why.
```
